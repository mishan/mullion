# The layout, as data

What a mullion layout is, how one that was kept is read back, and what is
kept. This is the part of mullion another implementation has to agree
with byte for byte, so that a layout made in one opens in the other: the
same model on the desktop, say, reading the layouts people made on the
web. `test/layouts.json` holds the cases every implementation is held to
(see [The cases](#the-cases)).

## The tree

A layout is a tree of two kinds of node, told apart by one field:

```ts
interface Leaf  { tabs: string[]; active?: number }
interface Split { dir: 'row' | 'col'; size: number[]; kids: Node[] }
type Node = Leaf | Split;
```

A node is a **leaf** when `tabs` is an array, and a **split** otherwise.

**A leaf** holds panes as tabs, by id, in strip order.

- `active` is which tab is in front. It is an index into the leaf's tabs
  **that are in play**: the page has the pane, and the pane's mode is up.
  A place kept for a pane still to come, or a pane whose mode is down, is
  in `tabs` and is not counted. Absent means 0.
- Once a leaf is drawn, `active` is clamped to the tabs in play, and the
  clamped value is what the layout holds from then on.

**A split** lays its children out side by side (`row`: dividers upright)
or stacked (`col`), in order.

- `kids` has two children or more.
- `size` has one number for each child, greater than 0. They are
  **shares, not fractions**: `[1, 1, 2]` gives the last child half. What
  is drawn is each share over the sum of the shares of the children that
  have anything in play, so a child whose panes are all away takes no
  room and leaves no gap.

Nothing else is part of the tree. Fields a node does not have are
ignored when it is read and not written back. Pixel sizes, zoom, focus
and where a closed pane came from are not in it.

Every pane the page has that no leaf holds is **closed**: in the drawer,
one click from coming back. The drawer is not stored; it is whatever the
tree does not hold.

## What is kept

The tree, as `JSON.stringify` writes it: no white space, keys in the
order above (`tabs`, `active`; `dir`, `size`, `kids`), every leaf with
its `active`, numbers in the shortest form that reads back as the same
double (`0.5`, `1`, `0.3333333333333333`).

A page that gives a `version` keeps the tree in an envelope:

```json
{"version":2,"layout":{"tabs":["a","b"],"active":0}}
```

The version is any JSON value, and compares as one: `2` is not `"2"`.

Names reserved for the envelope, which a reader ignores until it knows
them: `floating` (panes in windows of their own, on a desktop), `zoom`
(the pane filling the layout). A reader that does not know a field
ignores it, so an older one opens a newer layout with those panes in the
drawer.

## Reading a kept layout back

Two passes, and the first is all or nothing.

**1. Is it a layout at all?** Parse the text as JSON. With a version,
take `layout` from the envelope, and only if the envelope's `version`
equals the page's; without one, the value itself. Then check the shape
of the whole tree:

- a leaf: `tabs` is an array of strings; `active`, if present, is a whole
  number, 0 or more (`1.0` is a whole number, `1.5` and `"1"` are not);
- a split: `dir` is `"row"` or `"col"`; `kids` is an array of two or more
  nodes, each of which passes; `size` is an array of numbers greater than
  0, as long as `kids`.

Anything else, anywhere in the tree, and there is no layout: the text is
not JSON, the value is not an object, a share is 0, one child is wrong.
A layout half read is worse than the page's default.

**2. Keep what the page has.** Walk the tree in order:

- a tab is kept if the page has that pane, or has said it will add it
  (`later`), and it has not been kept already; a pane named twice stays
  where it is named first;
- a leaf with no tab left is dropped, and one with tabs keeps
  `active`, clamped to its last tab;
- a split with no child left is dropped; with one, it is replaced by that
  child; otherwise it keeps its children and their shares, in order.

If nothing is left, or what is left holds only places for panes still to
come, there is no layout.

**No layout** means the page's own default for the mode comes up (read
through step 2 as well), and with no default, every pane in one leaf in
the page's order.

## The cases

`test/layouts.json` is generated by `tools/layouts.mjs` from the list
there; `npm test` fails if it is out of date. Each case is:

| field | |
|---|---|
| `name` | what it holds an implementation to |
| `panes` | the page's panes, in order |
| `later` | panes the page will add, whose places are kept |
| `version` | the page's version, where it gives one |
| `stored` | the text that was kept, exactly, or `null` for nothing |
| `refused` | whether reading it gives no layout |
| `expect` | the layout that comes up: what was read, or every pane in one leaf |
| `written` | the text kept for `expect`, byte for byte |

With no default layout for the mode, an implementation that reads
`stored` has to come up with `expect`, and keep it as `written`.
`test/check.mjs` runs them all in the browser.
